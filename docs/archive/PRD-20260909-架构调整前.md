# Lunar Physical AI Companion v1.0 PRD

> **产品形态**：实体 AI Companion + 手机控制中心 + 云端智能  
> **原型硬件**：M5Stack StackChan Core + Faces Bottom3 + Faces Gamepad3  
> **核心定位**：低维护、会自己生活、能理解用户、能在现实场景中提供帮助的实体 AI 小伙伴  
> **版本**：v1.0 Draft · 2026-09-09 修订

---

## 本次确认的产品约束

- 保持通用 Companion 架构，支持更换角色身份、形象、人格、说话风格及声音设定；Lunar 是默认角色预设，不将其设定硬编码进业务逻辑。
- 保留首次使用的人格模板、声音选择，以及 Character / Brain 中的通用配置能力。v1.0 仍不做多个角色同时运行，更换设定不等于多角色系统。
- 自主生活和 AI 生成事件受当前生效的角色设定与结构化世界规则约束。每次生成保存所用角色预设及版本，后续更换设定不追溯改写历史。
- 将 AI 虚构小旅行与真实共同经历分开记录、检索和展示；不得把生成内容当作用户实际经历或已验证的现实事实。

## 1. 产品一句话

**Lunar 不是需要被照顾的电子宠物，也不是装进玩具里的 AI 助手。它是一个有自己生活节奏、能理解你、记得共同经历，并偶尔真正帮得上忙的实体 AI 小伙伴。**

---

## 2. 产品背景

现有 AI Companion 常见两类问题：

### 2.1 AI 聊天设备

优点：
- 对话能力强
- 信息能力强

问题：
- 本质仍像 ChatGPT 换了一个壳
- 需要用户主动发起对话
- 缺少“它一直在这里”的存在感

### 2.2 传统电子宠物

优点：
- 存在感强
- 有持续关系感

问题：
- 常依赖喂食、清洁、签到、任务等高维护操作
- 容易给用户形成负担

### 2.3 Lunar 的机会

Lunar 希望处于两者之间：

```text
传统电子宠物              AI Assistant
     │                         │
有存在感                     功能强
需要照顾                     缺少生命感
     │                         │
     └──────── Lunar ─────────┘

      自己生活 + 理解用户
      低维护 + 有现实能力
```

核心不是让用户“养 Lunar”，而是：

> **Lunar 在用户不操作的时候也像在生活，而用户需要它的时候，它又真的能提供帮助。**

## 4. v1.0 产品目标

v1.0 需要验证三个核心假设。

### 4.1 假设 A：用户会因为 Lunar“自己在生活”而持续回来查看

即使没有明确任务，用户也会自然产生：

> Lunar 今天在干嘛？

### 4.2 假设 B：现实能力可以强化陪伴关系

例如：

- Lunar 帮用户完成一次泰语交流
- Lunar 记得提醒拿快递
- Lunar 根据天气改变自己的行为
- Lunar 偶尔自己出门，回来带回一段经历

这些行为不只是工具调用，而会成为：

> “我和 Lunar 一起经历过的一件事。”

### 4.3 假设 C：Lunar 最终可以脱离手机独立存在

目标体验：

```text
用户拿起 Lunar
↓
直接陪伴 / 对话 / 翻译
↓
手机不参与核心使用链路
```

手机主要用于：

- 人格设定
- 模型设定
- 记忆管理
- 插件管理
- 设备管理

- 对现实环境产生反应

# 10. 小旅行 / 自主外出

## 10.1 定位

小旅行不是插件。

它属于：

> **Lunar 自主生活的一部分。**

## 10.2 用户体验

某天用户打开设备：

```text
┌────────────────────┐
│ 16:20        ☀ 29° │
│                    │
│                    │
│       空房间        │
│                    │
│  Lunar 出门了。     │
│                    │
└────────────────────┘
```

若干时间后：

```text
Lunar 回来了。

好像带了什么东西。
```

进一步查看：

```text
湿掉的饮料贴纸

“雨比想象中大。”
```

## 10.3 生成机制

v1.0 不使用纯预制事件池。

采用：

**结构化世界规则 + AI 动态生成内容**

AI 输入：

### 现实上下文
- 当前时间
- 天气
- 城市
- 季节
- 节日

### Lunar Context
- 性格
- 当前状态
- 最近行为

### Relationship Context
- 用户偏好
- 最近聊天摘要
- 共同记忆

AI 输出固定结构：

```text
去向
观察
纪念物
Lunar 一句话
```

示例：

```text
location:
便利店

observation:
店员趴在柜台上打瞌睡

souvenir:
一张热饮标签

comment:
“看起来大家今天都累。”
```

## 10.4 规则

AI 不决定世界规则。

系统决定：

- Lunar 能去哪里
- 什么情况下可以外出
- 什么情况下必须在家
- 允许出现哪些类型的物件

AI 负责：

> 在规则范围内生成差异化内容。

---

## 10.5 生成经历的来源与边界

小旅行属于角色世界中的虚构故事。天气、时间等真实输入可以影响故事，但不能证明故事中的地点、人物或事件真实发生过。

生成时：
- 使用当前角色的身份、性格、说话风格和边界，以及允许的地点、物件和行为规则。
- AI 只生成规则范围内的内容；系统校验结构、规则与重复度，不合格时重试或暂不生成，不写入已完成经历。
- 不生成用户参与过某事件的事实断言；用户未实际参与的小旅行不能被保存为“我们一起去过”。
- 记录 event_id、source_type、occurred_at、generated_at、character_preset_id、character_version，以及所用现实上下文的来源和采集时间。虚构故事时间与实际生成时间分别保存。
- 生成内容标记 source_type = fictional_trip；纪念物继承同一来源并关联 event_id。

展示时，回忆卡片使用“小旅行故事”等轻量来源标签；详情说明为角色想象经历，不在 Home 持续堆叠解释。

# 19. 回忆系统

## 19.1 定位

回忆不是完整日志。

它是：

> **Lunar 认为值得留下的共同经历。**

## 19.2 来源

- 小旅行
- 第一次使用某项能力
- 用户主动保存
- 特殊对话
- 特定地点
- 重要提醒
- AI 判断的重要事件

## 19.3 Core 展示

Core 只负责轻量浏览。

示例：

```text
SEP 19

在曼谷第一次
帮你用泰语点了东西。

♡
```

完整管理放在手机端。

---

## 19.4 来源分类与检索规则

每条记忆必须携带来源，至少区分：

| source_type | 含义 | 写入依据 |
|---|---|---|
| fictional_trip | AI 生成的小旅行故事 | 已通过校验的生成事件 |
| shared_experience | 用户与设备实际发生的共同交互 | 翻译完成、用户确认提醒等可追溯事件 |
| user_reported | 用户主动讲述的经历或事实 | 对话或用户录入，保留“用户自述”来源 |

- 真实交互的记录不得超出证据：完成翻译可以记录为“一次中泰翻译”，不能仅凭译文推断“在曼谷成功点餐”。
- AI 判断某内容值得保存，只影响筛选，不改变其来源或真实性等级。
- 回忆浏览可同时包含故事和真实经历，但卡片须有来源标签，并支持按来源筛选。
- 检索和对话上下文保留来源字段。回答“我们上次去哪里”时，不以 fictional_trip 作为现实经历的依据；提及故事时明确说“那次小旅行故事里”。
- 虚构经历不得自动写入 Profile 中的用户偏好、地点、关系或其他稳定事实。
- 用户可编辑、删除记忆；编辑不能默默抹除原始来源。用户确认的新增事实单独保存，并关联原记录。
- 更换角色设定后保留记忆来源与当时角色版本，不将旧角色经历改写为新角色的现实经历。

## 19.5 验收用例

1. AI 生成“去便利店带回贴纸”后，只出现小旅行故事和关联纪念物，不出现用户去过便利店的事实。
2. 用户问“我们上次去便利店是什么时候”，系统不会引用上述故事作为实际到访依据。
3. 完成一次中泰翻译，只记录可确认的翻译交互；未提供地点时不补写曼谷等位置。
4. 用户讲述一次旅行，记为用户自述，不能变成设备亲历。
5. 切换角色预设后，新故事使用新设定，旧故事仍保留原角色版本和来源。
6. 断网或生成校验失败时，不产生伪造的真实经历记录；本地生活状态继续运行。

# 33. 可落地性评估

## 33.1 高可行

- Home 桌宠
- 本地生命周期
- 时间 / 昼夜
- 提醒
- 按键体系
- Translator UI
- 手机人格配置
- 云端 AI 对话
- 云端记忆

## 33.2 重点验证

### 4G / eSIM

需要验证：
- 功耗
- 模块体积
- 天线
- 资费
- 稳定性

### 生成式小旅行

主要难点不是 AI 能不能生成，而是：

- 避免重复
- 避免 AI 味
- 保持世界观一致
- 内容不要过度戏剧化

### 续航

独立蜂窝网络 + 屏幕 + 音频会显著增加功耗。

这是 v1.0 最关键的硬件风险之一。

## 33.3 v1.0 不建议

Core 本地运行：

- 完整 LLM
- 完整 Whisper
- 高质量 TTS

Core 更适合承担：

> **身体、本能、状态、UI。**

而不是完整大脑。

# 35. 产品原则总结

后续每增加一个功能，都用以下问题判断：

1. 它是否让 Lunar 更像一个“存在”，而不是一个工具？
2. 用户是否必须主动管理它？如果是，是否真的有必要？
3. 它是否适合 320×240 小屏和实体按键？
4. 它是否值得占一个插件入口？
5. 它是否能够产生共同经历或现实价值？
6. 它是否可以在手机端配置，而不污染 Core 首页？
7. 它是否会增加用户维护压力？

如果答案偏离核心方向，则不进入 v1.0。

---

# 36. 最终产品定义

> **Lunar 是一个住在实体设备里的 AI 小伙伴。**
>
> 它平时有自己的生活节奏，不需要被照料；用户想说话时，它能理解并回应；需要帮助时，它可以翻译、提醒；不看它的时候，它也会继续生活，并把一些经历带回来。
>
> **它不是一个更小的手机，也不是一个更聪明的电子宠物，而是一个可以和你一起经历现实世界的 AI Companion。**
